Data Redundancy🔥 مهم
لما الـ organization تحتفظ بـ multiple files لنفس الموضوع بتحصل Data Redundancy وده معناه إن نفس البيانات بتتخزّن أكتر من مرة، وبكده بتضعف الـ Data Integrity.
📍 p.4
Database needs🔥 مهم
الـ database بتحقّق أربعة احتياجات أساسية.
  • Sharingالـ departments المختلفة بتشارك نفس المعلومات.
  • Securityكل user بيوصل لأجزاء معينة بس من البيانات.
  • Less Data Redundancyأي تحديث أو تغيير بيتم في مكان واحد.
  • Data Integrityبتساعد على إن البيانات تبقى دقيقة.
📍 p.4
Single-user vs Multi-user
الـ Single-user database بتدعم user واحد بس في الوقت، أما الـ Multi-user database فبتدعم أكتر من user في نفس الوقت.
Single-user
  • user واحد في الوقت
VS
Multi-user
  • أكتر من user في نفس الوقت
📍 p.5
Workgroup vs Enterprise
الاتنين Multi-user databases. الـ Workgroup بتخدم مجموعة صغيرة من المستخدمين أو department واحد، والـ Enterprise بتخدم مجموعة كبيرة أو المنظمة كلها.
Workgroup
  • Multi-user
  • مجموعة صغيرة أو department واحد
VS
Enterprise
  • Multi-user
  • مجموعة كبيرة أو المنظمة كلها
📍 p.6
Centralized vs Distributed
التصنيف هنا حسب مكان البيانات. الـ Centralized بتدعم بيانات موجودة في site واحد، والـ Distributed بتدعم بيانات موزّعة على أكتر من site.
Centralized
  • البيانات في site واحد
VS
Distributed
  • البيانات على أكتر من site
📍 p.7
Batch Processing
الفكرة إن البيانات بتتجمّع وبعدين بتتعالج كلها مرة واحدة، فالنتيجة بتيجي بعدين. بتتكرر كل يوم أو أسبوع أو شهر، زي فاتورة التليفون.
📍 p.8
Real-time Processing
الـ Real-time Processing هي معالجة البيانات online في نفس اللحظة، يعني النتيجة بتيجي دلوقتي. مثال على كده كارت الـ ATM.
📍 p.8
DBMS components🔥 مهم
الـ DBMS بيتكوّن من خمسة مكوّنات، وكل واحد منهم له دور محدد.
  • DBMS engineهو الجسر بين الـ logical view والـ physical view للبيانات.
  • Data definition subsystemبتوصف الـ logical structure للبيانات باستخدام الـ data dictionary.
  • Data manipulation subsystemأدوات لمعالجة البيانات وتحليلها، زي الـ SQL.
  • Application generatorأدوات لإنشاء الـ forms والـ reports.
  • Data administration subsystemبتساعد على إدارة الـ database كلها للحفاظ على الـ security والـ recovery وغيرهم.
📍 p.9 · p.10
DBA🔥 مهم
الـ DBA هو مدير الـ database. بيدير النظام وبيدّي الـ rights للـ users.
📍 p.10
Schema🔥 مهم
الـ Schema هو التنظيم الـ conceptual للـ database كلها زي ما الـ DBA شايفها. الرسم بيعرض كل الـ tables والروابط بينها: classroom, grade, course, student, parent, teacher, attendance, exam, exam_type, exam_result.
📍 p.11 · p.12
Subschema🔥 مهم
الـ Subschema بيحدّد الجزء من الـ database اللي بتشوفه الـ application programs اللي بتطلّع المعلومات المطلوبة. في الرسمين بيظهر جزء فيه exam_type, exam, exam_result. والجزء التاني فيه student و parent.
📍 p.11 · p.13 · p.14
Schema DDL🔥 مهم
الـ Schema DDL بتمكّن الـ DBA من تعريف مكوّنات الـ schema. أوامرها: CREATE و ALTER و RENAME و DROP و TRUNCATE.
📍 p.15
Subschema DDL🔥 مهم
الـ Subschema DDL بتسمح للـ application programs بتعريف مكوّنات الـ database اللي هتستخدمها.
📍 p.15
DML🔥 مهم
الـ DML بتعرّف خصائص البيانات وهيكلها عشان يتم التعامل مع البيانات. أوامرها: SELECT و INSERT و UPDATE و DELETE.
📍 p.15
Data types
أنواع البيانات من اللبنات الأساسية للـ data model: Audio, Music, Photographs, Video. وكمان الـ Alphanumeric اللي بتشمل Text, Numbers, Currency, Date/Time, Yes/No.
📍 p.16
Data organization🔥 مهم
تنظيم البيانات بيتدرّج من أصغر مستوى لأكبر مستوى.
  • Characterحرف واحد، وهو أصغر مستوى في تنظيم البيانات.
  • Field (Attribute)مجموعة من الـ characters المرتبطة ببعض، زي الـ Name والـ Tel. No. والـ address.
  • Recordمجموعة من الـ fields المرتبطة ببعض.
  • File (Entity)مجموعة من الـ records المرتبطة ببعض.
  • Databaseمجموعة من الـ files المرتبطة ببعض.
كل مستوى مجموعة من المستوى اللي قبله
Character→Field→Record→File→Database
📍 p.17
الجدول كـ Entity🔥 مهم
الجدول بيمثّل الـ Entity. والصف الواحد فيه هو الـ Record. والعمود هو الـ Field. الجدول اللي في الرسم بيحتوي على الـ ID والـ name والـ address والـ city لكل Employee.
📍 p.18
Entity🔥 مهم
الـ Entity هو أي حاجة بنجمع ونخزّن بيانات عنها، زي Person أو Department أو Car.
📍 p.19
Attribute🔥 مهم
الـ Attribute هو صفة من صفات الـ entity.
📍 p.19
Relationship🔥 مهم
الـ Relationship بتوصف ارتباط بين اتنين أو أكتر من الـ entities. أنواعها تلاتة. الأول 1:M وهو One-to-many. التاني M:N أو M:M وهو Many-to-many. التالت 1:1 وهو One-to-one.
📍 p.19

الـ data models اتطوّرت من Hierarchical لـ Network ثم Relational.
ترتيب تطوّر الـ data models
Hierarchical→Network→Relational

Evolution of data models
الـ data models اتطوّرت على تلات مراحل رئيسية بالترتيب ده.
Hierarchical→Network→Relational
📍 p.2
Hierarchical structure
الـ hierarchical structure شكله tree. فيه root segment وتحته levels من الـ segments وكل level هو الـ children بتاعة اللي فوقه. في الرسم الأول الـ root هو Final Assembly وتحته Components ثم Assemblies ثم Parts. والأمثلة التانية بتوضّح نفس الفكرة: library collection بتتقسم لـ subject areas ثم authors ثم books. وكمان department فيه manager و employee و task.
📍 p.3 · p.4 · p.5
Hierarchical characteristics🔥 مهم
الـ hierarchical structure ليه أربع خصائص أساسية.
  • Nodesالـ fields والـ records بتتنظّم في nodes.
  • Parent and childالـ parent node ممكن يبقى له many children nodes والـ child node له one parent node بس.
  • Tree pathالـ tree بيتعرّف بالـ path اللي بتتبع الـ parent segments لحد الـ child segments من الشمال.
  • Tree traversalليه طرق مختلفة زي الـ Preorder traversal.
📍 p.6
Hierarchical advantages
من مميزات الـ hierarchical model الـ Conceptual simplicity والـ Database security والـ Data independence. وكمان تنفيذ 1:1 و 1:M سهل.
📍 p.7
Hierarchical disadvantages
من عيوب الـ hierarchical model إن التنفيذ معقّد والإدارة صعبة وتنفيذ M:N صعب وبرمجة التطبيقات واستخدامها معقّدين. وكمان فيه Lack of structural independence. ولو الـ parent node اتمسح بالغلط كل الـ children nodes بتتمسح.
📍 p.8
Network structure🔥 مهم
الـ network model شبه الـ hierarchical وهو مجموعة records في علاقات 1:M. الفرق إن الـ child ممكن يبقى له many parents وكل parent برضو ممكن يبقى له many children.
  • Ownerبيعادل الـ parent في الـ hierarchical model.
  • Memberبيعادل الـ child في الـ hierarchical model.
📍 p.9
Network model figure
الرسم بيوضّح إن الـ record ممكن يبقى له أكتر من owner. الـ invoice بتتوصل بـ owners اتنين هم salesrep و customer. والـ inv_line بتتوصل بـ owners اتنين هم product و invoice. وكل اتصال بيتسمّى set.
📍 p.10
Network advantages
من مميزات الـ network model الـ Conceptual simplicity وإنه بيتعامل مع relationship types أكتر والـ Data access flexibility.
📍 p.11
Network disadvantages
من عيوب الـ network model الـ System complexity والـ Lack of structural independence.
📍 p.12
RDBMS🔥 مهم
الـ RDBMS بتعمل نفس الوظائف الأساسية بتاعة الـ hierarchical والـ network DBMS وبتزيد عليها وظائف تانية. وأهم ميزة فيها إنها بتخلّي الـ user أو الـ designer يشتغل في human logical environment.
📍 p.13
Relational table🔥 مهم
الـ table أو الـ relation هو matrix فيه series من تقاطعات الـ row والـ column. والجداول بترتبط ببعض عن طريق مشاركة common entity characteristic.
📍 p.14
Relational schema🔥 مهم
الـ relational schema هو تمثيل بصري للـ entities والـ attributes اللي جواها والـ relationships بينها.
📍 p.14
Linking relational tables
الرسمين بيوضّحوا إن الجداول بتتوصل ببعض عن طريق characteristic مشترك بينها. الـ agent و الـ customer بيتوصلوا عن طريق agent_code. والـ agent الواحد بيبقى له many customers.
📍 p.15 · p.16
Purely logical table
الـ relational table بتخزّن collection من الـ entities المرتبطة ببعض وبتشبه الـ file. وهي purely logical structure يعني طريقة التخزين الفعلي للبيانات مش بتهم الـ user ولا الـ designer. والخاصية دي بقت مصدر database revolution حقيقية.
📍 p.17
Relational advantages
من مميزات الـ relational model الـ Structural independence والـ Improved conceptual simplicity وسهولة تصميم الـ database وتنفيذها وإدارتها واستخدامها والـ Ad hoc query capability والـ Powerful database management system.
📍 p.18
Relational disadvantages
من عيوب الـ relational model إن فيه overhead كبير على الـ hardware والـ system software. وكمان ممكن يسهّل التصميم والتنفيذ السيّئ. وممكن يعمل مشاكل islands of information.
📍 p.19
Entity relationship model🔥 مهم
الـ Entity Relationship model هو graphical tool مقبول ومستخدم على نطاق واسع في data modeling. قدّمه Chen سنة 1976 وبيمثّل الـ entities وعلاقاتها في الـ database structure بشكل graphical.
📍 p.20
ERD structure🔥 مهم
الـ ERD بيستخدم graphic representations لتمثيل مكوّنات الـ database. والـ entity فيه بيتحوّل لـ relational table.
  • Entity instanceهو الـ row في الـ table. ويتسمّى كمان occurrence.
  • Entity setهو collection من الـ entities المتشابهة.
  • Connectivityبتوصف نوع الـ relationship. وبتتمثّل بـ diamond متوصل بالـ entities المرتبطة عن طريق relationship line.
📍 p.21
Chen and Crow's Foot ERD
الرسمين بيعرضوا نفس أنواع الـ relationships بـ notation مختلفة. في الـ Chen الـ relationship بتتمثّل بـ diamond وعليها labels زي 1 و M و N. أما الـ Crow's Foot فبتستخدم رموز على الخط نفسه. والأنواع هي 1:M و M:N و 1:1.
📍 p.22 · p.23
ER advantages
من مميزات الـ ER model الـ Exceptional conceptual simplicity والـ Visual representation والـ Effective communication tool والتكامل مع الـ relational data model.
📍 p.24
ER disadvantages
من عيوب الـ ER model الـ Limited constraint representation. وكمان مفيهوش data manipulation language. وفيه Loss of information content.
📍 p.25
Development of data models
الـ semantics في الـ data models بتزيد من الأقل للأكتر.
  • Hierarchical and Networkأقل semantics. صعب فيهم تمثيل M:N (في الـ hierarchical بس) وفيهم physical level dependency ومفيش ad hoc queries. والـ access path predefined (navigational access).
  • Relationalبيدّي ad hoc queries و set-oriented access لكن الـ semantic content بتاعه ضعيف.
  • Entity Relationshipسهل الفهم وبيشمل semantics أكتر.
  • Semanticفيه semantics أكتر ويدعم complex objects والـ inheritance والـ behavior. وبيتفرّع لـ Object-Oriented و Extended Relational (Object/Relational).
الـ semantics بتزيد من الأقل للأكتر
Hierarchical and Network→Relational→Entity Relationship→Semantic
📍 p.26
Data abstraction🔥 مهم
الـ data abstraction هي الخاصية اللي بتسمح بنوعين من الـ independence.
  • Program-data independenceالـ program مستقل عن طريقة تخزين البيانات الفعلية.
  • Program-operation independenceالـ program بينفّذ operations من غير ما يهمه الـ operations دي متنفّذة إزاي.
📍 p.27
ANSI/SPARC degrees🔥 مهم
الـ ANSI/SPARC صنّفت الـ data models في السبعينات حسب الـ degree of abstraction لأربع درجات.
  • Conceptualأعلى degree of abstraction وبيمثّل الـ global view.
  • Externalالـ view بتاع الـ end users.
  • Internalالـ database زي ما الـ DBMS شايفها.
  • Physicalأقل مستوى وبيوصف طريقة تخزين البيانات.
الـ Conceptual أعلى abstraction والـ Physical أقل
Conceptual→External→Internal→Physical
📍 p.28 · p.29
Data abstraction levels
الرسم بيوضّح إن الـ Conceptual عنده degree High وهو hardware و software independent. والـ Internal عنده degree Medium وهو software dependent و hardware independent. والـ Physical عنده degree Low وهو hardware و software dependent. والـ External models اتنين بيتوصلوا بالـ Internal.
📍 p.29
Conceptual model🔥 مهم
الـ Conceptual model بيمثّل الـ global view للـ database زي ما الـ high-level managers شايفينها. وهو أساس تحديد ووصف الـ main data objects من غير تفاصيل. وأكتر conceptual model استخدامًا هو الـ Entity Relationship (ER) model.
📍 p.30
Conceptual model figure

Conceptual model advantages🔥 مهم
الـ conceptual model بيدّي macro level view لبيئة البيانات سهل الفهم نسبيًا. وهو مستقل عن الـ software والـ hardware الاتنين يعني مبيعتمدش على الـ DBMS software ولا على الـ hardware. وأي تغيير فيهم ملوش تأثير على تصميم الـ database على مستوى الـ conceptual.

Internal model
الـ Internal model هو تمثيل الـ database زي ما الـ DBMS شايفها. وبيحوّل الـ conceptual model ليناسب الـ DBMS. وهو software dependent لكن hardware independent.
📍 p.33
External model🔥 مهم
الـ External model هو view الـ end users لبيئة البيانات. الـ modeler بيقسّم الـ requirements والـ constraints لـ functional modules ويفحص كل module جوه إطار الـ external model بتاعه. والتصميم الجيد لازم ياخد في اعتباره العلاقات بين الـ views ويدّي الـ programmers set of restrictions بتحكم الـ common entities.
📍 p.34
Division into external models
الرسم بيوضّح تقسيم الـ internal model لـ external models. كل programmer بياخد subset من التصميم يخص شغله. Jim بياخد الـ student والـ enroll والـ class. و Anne بتاخد الـ room والـ class والـ professor.
📍 p.35
External model advantages🔥 مهم
للـ external models أربع مميزات أساسية.
  • Application programsاستخدام الـ database subsets بيخلّي تطوير الـ application programs أبسط بكتير.
  • Designer's taskبيسهّل على الـ designer تحديد البيانات المطلوبة لدعم عمليات كل business unit.
  • Conceptual feedbackبيدّي feedback عن مدى كفاية الـ conceptual model.
  • Security constraintsعمل الـ external models بيساعد على ضمان الـ security constraints في تصميم الـ database.
📍 p.36
External model dependency
الـ External model هو DBMS dependent لكن hardware independent.
📍 p.37
External models figure
الرسم بيوضّح external models لوحدتين في شغل الكلية هما student registration و class scheduling. في الـ registration الـ student ممكن ياخد لحد ست classes والـ class محدود بـ 35 student. وفي الـ scheduling الـ room بتتستخدم لـ many classes وكل class بيتدرّس في room واحدة وعن طريق professor واحد، والـ professor بيدرّس لحد تلات classes.
📍 p.38
Physical model🔥 مهم
الـ Physical model بيشتغل على أقل مستوى من الـ abstraction وبيوصف الطريقة اللي البيانات بتتخزّن بيها على storage media زي الـ disks أو الـ tapes. وهو software و hardware dependent. وبيحتاج من الـ database designers معرفة تفصيلية بالـ hardware والـ software اللي هيتنفّذ بيهم التصميم.

E-R model🔥 مهم
الـ E-R model هو تمثيل logical ومفصّل للبيانات الخاصة بـ organization أو business area. وبيتعبّر عنه بالـ entities في بيئة الشغل والـ relationships أو associations بينها والـ attributes أو properties بتاعة الـ entities وعلاقاتها.
📍 p.2
Entities🔥 مهم
الـ entity هو person أو place أو object أو event أو concept بنحب نخزّن بيانات عنه.
  • Personشخص بنحب نخزّن بيانات عنه، زي EMPLOYEE و STUDENT و PATIENT.
  • Placeمكان زي CITY و STATE و COUNTRY.
  • Objectحاجة مادية زي MACHINE و BUILDING و AUTOMOBILE.
  • Eventحاجة بتحصل زي SALE و REGISTRATION و RENEWAL.
  • Conceptفكرة مجردة زي ACCOUNT و COURSE و WORK CENTER.
📍 p.3
Attributes🔥 مهم
الـ attribute هو property أو characteristic للـ entity. مثلًا الـ STUDENT ليه Student_ID و Student Name و Address. والـ AUTOMOBILE ليه Vehicle_ID و Color و Weight و Horsepower.
📍 p.4
Relationships
الـ relationship هو association بين entity أو أكتر ومهم للـ organization.
📍 p.5
Basic symbols🔥 مهم
لكل عنصر في الـ E-R diagram رمز مختلف.
  • Strong entityبيتمثّل بـ rectangle عادي.
  • Weak entityبيتمثّل بـ rectangle بخط مزدوج.
  • Associative entityبيتمثّل بـ diamond جوه rectangle.
  • Simple or composite attributeبيتمثّل بـ ellipse عادي.
  • Multi-valued attributeبيتمثّل بـ ellipse بخط مزدوج.
  • Derived attributeبيتمثّل بـ ellipse بخط متقطّع.
  • Relationshipبيتمثّل بـ diamond.
  • Identifying relationshipبيتمثّل بـ diamond بخط مزدوج.
📍 p.6
Attribute types🔥 مهم
الـ attributes ليها تلات أنواع أساسية حسب إمكانية تقسيمها وعدد القيم.
  • Simple attributeمينفعش يتقسّم لمكوّنات أصغر زي Student_ID.
  • Composite attributeممكن يتقسّم لمكوّنات أصغر زي Address.
  • Multi-valued attributeممكن ياخد أكتر من value للـ entity instance الواحدة زي Courses.
📍 p.7
Derived and key attributes🔥 مهم
في كمان تلات أنواع تانية من الـ attributes.
  • Derived attributeقيمته بتتحسب من attributes تانية مرتبطة بيه زي Student_Age.
  • Key attributeبيحدّد كل instance من الـ entity بشكل فريد. ويتسمّى كمان Identifier. مثال عليه Student_ID.
  • Composite key attributeهو key attribute متكوّن من composite attribute زي Flight_ID.
📍 p.8
Attribute diagrams
الرسومات بتوضّح رموز الـ attributes على entity واحدة. الـ key attribute اسمه بيتحط تحته خط، والـ derived attribute ellipse متقطّع، والـ multi-valued ellipse مزدوج. والـ composite attribute بيتفرّع لمكوّنات زي Address اللي بيتقسّم لـ Street_Address و City و Country و Postal_Code. والـ composite key زي Flight_ID اللي بيتقسّم لـ Flight_Number و Flight_Date.
📍 p.9 · p.10 · p.11
Entity type
الـ entity type هو وصف للـ entity باستخدام metadata. وبيتوصف مرة واحدة بس في الـ database. الجدول بيوصف EMPLOYEE بـ attributes زي Employee_Number و Name و Address و City و Zip و Date_Hired و Birth_Date مع نوع كل واحد.
📍 p.12
Entity instance
الـ entity instance هو single occurrence من الـ entity type. في الجدول بيظهر instances اتنين من EMPLOYEE بقيم مختلفة لنفس الـ attributes.
📍 p.13
Strong weak and associative entities🔥 مهم
في تلات أنواع من الـ entity types حسب استقلالها.
  • Strong entity typeentity type بيوجد بشكل مستقل عن باقي الـ entity types.
  • Weak entity typeentity type وجوده بيعتمد على entity type تاني اسمه owner.
  • Associative entityentity type بيربط instances من entity type أو أكتر وبيحتوي attributes خاصة بالـ relationship بين الـ instances دي.

الرسم بيوضّح weak entity اسمها DEPENDENT بتعتمد على الـ EMPLOYEE. بتتمثّل بـ rectangle مزدوج، والـ relationship بينهم Has بتتمثّل بـ diamond مزدوج لأنها identifying relationship.
📍 p.15
Relationship type🔥 مهم
الـ relationship type هو association ليه معنى بين entity types. وأنواعها هي 1:1 و 1:M و M:N.
📍 p.16
Relationship instance🔥 مهم
الـ relationship instance هو association بين entity instances. وكل instance فيها entity واحدة بالظبط من كل entity type مشاركة. في الرسم الـ instances بتربط الطلبة بالكورسات اللي أخدوها.
📍 p.17
Attributes on relationships🔥 مهم
الـ attributes ممكن تتربط بـ relationship زي ما بتتربط بـ entity. مثلًا لو الـ organization عايزة تسجّل شهر وسنة إتمام كل student لكل course بتتضاف attribute اسمها Date_Completed على الـ relationship.
📍 p.18 · p.19
Associative entity🔥 مهم
وجود attribute أو أكتر على relationship بيقترح على الـ designer إنه يمثّل الـ relationship كـ associative entity. والـ associative entity بيربط instances من entity type أو أكتر وبيحتوي attributes خاصة بالـ relationship. في الرسم Completes اتحوّلت لـ COMPLETING ومعاها Certificate_Number و Date_Completed.
📍 p.20 · p.21
Degree of relationships🔥 مهم
الـ degree هو عدد الـ entity types المشاركة في الـ relationship. وأشهر تلات أنواع هي الـ unary بـ degree 1 والـ binary بـ degree 2 والـ ternary بـ degree 3. وفي degrees أعلى لكنها نادرة الحدوث في الواقع.
📍 p.22
Unary relationship🔥 مهم
الـ unary relationship بين instances من entity type واحد، ويتسمّى كمان recursive relationship. في الرسم PERSON له Is_married_to بنوع one-to-one. و EMPLOYEE له Manages بنوع one-to-many. و ITEM له Has_Sub-item بنوع many-to-many ومعاه attribute اسمها Quantity.
📍 p.23
Binary relationship🔥 مهم
الـ binary relationship بين instances من entity types اتنين، وهي أكتر نوع شيوعًا في الـ data modeling. في الرسم EMPLOYEE مع PARKING PLACE بنوع one-to-one. و CUSTOMER مع ORDER بنوع one-to-many. و STUDENT مع COURSE بنوع many-to-many.
📍 p.24
Ternary relationship🔥 مهم
الـ ternary relationship هي simultaneous relationship بين instances من تلات entity types. في الرسم Supplies بتربط VENDOR و PART و WAREHOUSE ومعاها attributes هي Shipping_mode و Unit_Price.
📍 p.25
Ternary versus three binaries🔥 مهم
الـ ternary relationship مش نفس تلات binary relationships. الـ attribute زي Unit_Price مينفعش يتربط صح بواحدة من الـ binary relationships التلاتة. مثلًا لو قلنا إن vendor X يقدر يشحن part C بسعر 80 L.E تبقى البيانات incomplete لأنها مش بتحدد الـ warehouse اللي هتتشحن ليه. ووجود attribute على Supplies بيقترح تحويلها لـ associative entity زي SUPPLY SCHEDULE.
📍 p.26 · p.27
Cardinality constraint🔥 مهم
الـ cardinality بتحدّد العلاقة من ناحية العدد.
  • Cardinality constraintبيحدّد عدد instances بتاعة entity ممكن أو لازم ترتبط بكل instance من entity تانية.
  • Minimum cardinalityهو أقل عدد instances من entity ممكن يرتبط بكل instance من entity تانية.
  • Participationممكن تبقى optional أو mandatory. لو الـ minimum cardinality صفر تبقى optional ولو 1 تبقى mandatory.
📍 p.28
Cardinality examples
الرسمين بيوضّحوا إزاي الـ cardinality بتتقرا كـ business rules. الـ student ممكن ينجح في صفر أو واحد أو أكتر exams. والـ exam لازم ينجح فيه واحد أو أكتر students. وفي المثال التاني الـ customer ممكن يقدّم صفر أو أكتر orders. والـ order لازم يتقدّم من customer واحد بس.
📍 p.29 · p.30

📍 p.31
Case study business rules🔥 مهم
الـ business rules بتتكتب بصياغة ثابتة بتترجم لرموز الـ cardinality. في الـ case study الـ shipment لازم يتبعت من supplier واحد بس، والـ supplier ممكن يبعت صفر أو أكتر shipments. الجدول بيلخّص الصياغات.
